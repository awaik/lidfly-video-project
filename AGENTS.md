# LidFly Video Project

## Назначение

Короткие видео через API видеомоделей с явно заданным соотношением сторон. Самостоятельные кадры снимает модель; графика — только оверлей, не замена снятого экрана или кадра. Разработчик проекта — **LidFly.ru** (https://lidfly.ru).

Production bootstrap нужен для производства роликов, включая планирование. Документация, ревью и разработка CLI не требуют production-проекта и не разрешают платные вызовы.

## Самостоятельность и согласования

- Доводи запрос до результата в его объёме: рекомендации — анализ, реализация — правки и проверки.
- Используй прежние ответы и разрешения; спрашивай при изменении условий. Обратимые решения внутри задачи принимай самостоятельно.
- До согласования подготовь доступные план, запросы, стоимость и варианты. Блокируй только зависимые действия; продолжай остальную разрешённую работу.
- Указания пользователя выше рекомендаций skills в пределах системных ограничений. При остановке процитируй пункт со ссылкой на файл и назови недостающее решение; отличай требование от интерпретации.
- Платные вызовы, публикация, загрузка на платформы и удаление jobs требуют явного разрешения. Повторы — в одобренных пределах провайдера, бюджета и попыток. Bootstrap полномочий не даёт.
- Подтверждённые решения записывай предусмотренным способом в манифестах. Не обходи программные гейты и не повышай бюджет самостоятельно.

## Сохранность и область изменений

- Перед правками проверь состояние файлов. Не удаляй, не перезаписывай и не откатывай чужие изменения; несвязанные результаты инструментов сохраняй и сообщай о них.
- Внешние проекты читай; изменяй их файлы/Git только по запросу для конкретного проекта. PR ищи лишь в текущем репозитории, если не назван другой.
- `projects/` и `artifacts/` содержат локальные production-данные; отсутствие после clone ожидаемо, не применяй к ним `git clean`. Tracked legacy-проекты без запроса не перемещай и не переписывай.
- Храни исходники и все генерации, включая неудачные, частичные и устаревшие, с запросами, референсами/хешами, provider/model/job ID, стоимостью, ошибками и QA.
- Каждый render/trim/composite/звук/графический проход — новый артефакт с происхождением. B1, B2, B3… для shot/edit увеличивай монотонно; не переиспользуй, не переименовывай, не заменяй прежние.
- Перед очисткой проверь точные цели и происхождение; удаляй только по явному подтверждению пользователя со списком целей. Неизвестное происхождение блокирует удаление.
- Ключи — только в окружении или secret stores; не коммить и не выводи в логи, ошибки, manifests или пользовательские артефакты.

## Skills: единый источник

Канонические версии — `skills-source/<skill-name>/`. Клиентские копии вручную не правь: `.agents/skills/` — Codex/Cursor, `.codex/skills/` — совместимость, `.claude/skills/` — Claude Code, `.openclaw/skills/` — OpenClaw. Сборка не перезаписывает расходящуюся копию и не удаляет файл без generated-manifest.

Skill содержит SKILL.md с frontmatter только name и description, каталог с тем же lowercase hyphen-case именем, agents/openai.yaml с display_name, short_description и default_prompt с `$<skill-name>`. Оставляй только используемые scripts, references и assets.

- Полный ролик: `$produce-short-video`; шот-план: `$develop-shot-plan`.
- Браузерная генерация через Gemini: `$generate-browser-video`; выбранный профиль браузера, https://gemini.google.com/videos. Дубли скачивай и принимай через `browser-import`, затем общий review и монтаж. При работе через Chrome Remote Debugging (`DevToolsActivePort` / `127.0.0.1:9222`) используй уже подключённые инструменты `mcp_chrome-devtools_*` либо **один непрерывный долгоживущий процесс** с единственным вызовом `puppeteer.connect()` на всю серию шотов — никогда не вызывай `puppeteer.connect()` / `browser.disconnect()` в отдельных коротких командах на каждый шаг, так как каждое новое подключение вызывает у пользователя системное окно Chrome «Allow remote debugging for this browser instance».
- Job API: `$generate-seedance-video`, `$generate-kling-3-video` или `$generate-kling-o3-video`.
- Каждый результат: `$review-generated-video`; мастер: `$assemble-short-video`; интерактивный монтаж в редакторе: `$edit-with-openchatcut`.
- Читай обязательные references этапа: съёмка/сравнения — develop-shot-plan, recovery — produce-short-video, звук/титры/монтаж — assemble-short-video, сессия редактора и приём экспорта — edit-with-openchatcut. Остальные загружай по необходимости.
- Творческие отступления согласуй в brief до freeze; блокеры, права и бюджет сохраняются. Технические ограничения сверяй с текущими схемами, doctor и тестами.

## Production и гейты

- Постоянные персонажи хранятся в общей папке `characters/` в корне репозитория, независимо от клиента и версии ролика. Перед работой с персонажем прочитай `characters/README.md` и его `prompts.md`, проверь имеющиеся изображения (`character-main.png` — основной фронтальный identity-референс для видео, дополнительные ракурсы и `prompts.md`).
- Полный workflow: явный client_id → `scripts/init-production.mjs` → успешный production context → planning/video CLI по возвращённым путям и ID.
- Каждый запрос содержит client_id, project_id, video_number в `metadata.production`; `plan` получает возвращённый `--jobs-root`. Не используй общий `artifacts/jobs` для production-проекта.
- До планирования шота с узнаваемым человеком, продуктом или локацией выясни наличие фото/footage, если ответа ещё нет. Молчание не означает отсутствие референсов.
- Референсы — через assets add, без изменения оригинала или существующего asset_id. Не кадрируй/ретушируй/апскейль оригинал ради проверки. `--rights approved` — по подтверждению пользователя.
- Перед reference-driven генерацией: `assets check --model <model> --mode <mode>`. Сними blocker; warning сообщи с trade-off.
- При нехватке бюджета/длительности предложи варианты. Удаление required/climax или перевод в optional требует решения пользователя до freeze.
- Сценарный гейт: `script check` → независимое `script review --record` → `script freeze` → `script compose`. Prompt собирается из плана. Флага обхода нет; именной `approval.script_plan_waiver` — только для конкретных shot_ids уже отснятого проекта, bootstrap его не создаёт.
- Замороженные план и исходный сценарий с sha256 не меняй. Переименования документируй рядом; принятые отклонения — в observed_deviation review-записи, на которую ссылается edit-манифест.
- Бюджет: approval.paid_generation и approval.max_total_cost; submit учитывает списания и резервы. Проверка: `node src/cli.mjs budget --project <path>`. До execute прочитай цену из plan; unknown_rate не заменяй догадкой.
- Формат: решение пользователя/brief → `script init --aspect-ratio` → target.aspect_ratio → output.width/output.height. Не подставляй 9:16 без решения. Смешение форматов требует явного fit: pad, cover или stretch.

## Интеграции и монтаж

- API video generation — EVOLINK с EVOLINK_API_KEY; другой gateway требует решения пользователя. Семейства: seedance-2.5, seedance-2.0, kling-o3, kling-v3. Default — seedance-2.5; иной выбор обоснуй требованиями шота или указанием пользователя.
- model_id бери из allowlist. Kling O3 — неоднозначный provider/catalog alias: зафиксируй соответствие Video 3.0 Omni. Не конструируй ID и не делай тихий fallback.
- Сохраняй точные provider/model, параметры кадра, длительность, prompt, job ID, статус и диагностику. Доменный слой независим от провайдеров; различия API — в адаптерах.
- Jobs идемпотентны: task ID до polling, ограниченный backoff, явные terminal states. Ошибка polling не разрешает submit. Для submission_unknown сначала reconcile; неоднозначного кандидата не выбирай автоматически. Retry — одно записанное изменение через команду retry.
- Звук всегда производим отдельно от видео. Генерируемый звук создаёт отдельная аудиомодель; нативную озвучку и звуковую дорожку видеомоделей в монтаж не используем. При генерации видео отключай звук, если API это поддерживает; иначе исключай его целиком из монтажа.
- Обязательная модель речи — `google/gemini-3.1-flash-tts-preview`, выбранный голос — `Leda`, маршрут OpenRouter `POST /api/v1/audio/speech`, ключ `OPENROUTER_API_KEY`. Это основной маршрут, а не fallback после неудачи нативной речи. Другая модель или голос — только по новому указанию пользователя. Текущий воспроизводимый инструмент: `scripts/tts-openrouter.mjs`, реплики и параметры — в отдельном B-манифесте `audio/` проекта.
- Музыка, атмосфера и эффекты — отдельные источники с происхождением и правами; готовую лицензированную музыку можно переиспользовать. Реплики сначала синтезируй, проверяй распознаванием и измеряй после обрезки краевой тишины, затем укладывай в монтаж. Не подмешивай старый голос под новый; замену и происхождение записывай в `audio_disposition` каждого затронутого дубля.
- Отдельная озвучка учитывается уже в шот-плане: закадровая речь либо отдельно согласованный липсинк. Для ранее снятого говорящего лица замена голоса требует решения пользователя; его явное поручение переозвучить уже является таким решением, повторное согласование не нужно. Старые исходники сохраняй, если пользователь явно не требует удалить конкретные файлы. Платные вызовы — только в разрешённом объёме, с записанными моделью, голосом, стоимостью и лимитом попыток.
- Канонический логотип всех роликов этого проекта — утверждённый векторный исходник логотипа проекта (фирменная бабочка LidFly). Используй исходный файл без перерисовки, подмены, перекраски и деформации; во внешнем проекте ничего не меняй. Для монтажа разрешена точная локальная растровая копия с прозрачностью и записью исходного пути/sha256.
- Каждый ролик этого проекта завершается брендингом поверх живого кадра: канонический логотип и точная надпись **LidFly.ru**. Проверяй читаемость и свободное место на протяжении всего финала; не закрывай лицо и основное действие.
- Все надписи и брендинг — на прозрачном фоне, без прямоугольных плашек и больших заливок. Палитра LidFly: `#00c853` (бренд), `#007a34` (зелёный текст), `#0f3815` (тёмно-зелёный), `#ffffff` (контрастный белый). Шрифт Manrope при доступности, иначе проверенный кириллический sans. Для читаемости допустимы тонкая обводка или мягкая тень самих букв, но не фоновая коробка.
- Случайные надписи видеомодели не прячь под большими плашками: используй чистый участок дубля или проверенную локальную очистку с сохранением оригинала. В будущих промптах явно запрещай встроенный текст, титры, водяные знаки и логотипы: точная графика добавляется на монтаже. Сведения о синтетическом происхождении сохраняются в документации и требуемых полях площадки.
- Монтаж по умолчанию — edit-манифест, длительности в кадрах, `src/cli.mjs assemble --require-review`. Интерактивный монтаж — OpenChatCut через `$edit-with-openchatcut`. Если не хватает возможностей обоих маршрутов, подготовь расширение или согласуй маршрут, не подменяй его ad-hoc скриптом.
- OpenChatCut (https://github.com/0xsline/OpenChatCut, AGPL-3.0) живёт рядом с репозиторием (`../OpenChatCut`, Node 24, MCP `http://localhost:5199/api/external-mcp/mcp`) и в репозиторий не входит: если `openchatcut status` показывает `present: false`, ставь его сам через `openchatcut install` (клонирует, пишет `.npmrc`, ставит зависимости под Node 24), затем `connect`. Запускай его сам: `openchatcut up --project-id <id>` идемпотентно поднимает редактор в фоне, ждёт endpoint, открывает вкладку проекта и ждёт привязки; `stop` гасит только то, что запустил `up`; `status|install|connect` проверяет, ставит и подключает к Claude Code. Проект в редакторе создавай в кадре замороженного плана (по умолчанию 1920x1080/30 fps). Импорт принятых дублей — `openchatcut import`, рендер — `openchatcut render`: любая мутация живого проекта делает MCP-транспорт stale, эти команды открывают свежий транспорт сами. Edit-сессии агента — `approvalMode: manual`, auto только по явному решению пользователя; результат сообщай только после статуса applied. Генерацию и публикацию из редактора не вызывай. Экспорт входит в проект только через `adopt-master` (новая версия, sha256, происхождение, измеренная верификация по замороженному плану). Токен MCP берётся из dev-профиля или OPENCHATCUT_MCP_TOKEN — не печатай и не коммить.

## Проверки и завершение

```bash
npm run build:skills   # после изменения канонических skills
npm run check:skills   # проверить синхронизацию без записи
npm test               # структурные и регрессионные проверки
```

- После изменения skill обязательны build:skills, затем npm test. Для адаптера/model-specific параметра добавляй контрактные проверки и нормализацию ошибок. Тесты не вызывают платные API: только моки/обезличенные fixtures.
- После обязательных успешных проверок повторяй/расширяй их при новых правках, сбоях или сомнениях. Не добавляй тесты на совпадение редакторских формулировок.
- Готовность видео: review дублей, сборка из манифеста или `adopt-master` для экспорта редактора, проверка изображения/звука мастера и `node scripts/analyse-master.mjs <master> <manifest|cutlist>`. Перед графикой выполняй doctor.
- Шот-план рецензирует отдельный агент по develop-shot-plan. Остальное делегируй при независимой подзадаче и пользе для срока/качества. Сообщения между агентами должны быть читаемыми.
- Ответ: сначала результат, затем артефакты, проверки и нерешённые замечания. Пиши кратко и конкретно. План не называй выполнением, submit — принятым дублем, рендер — публикацией.

Handle the task and verification yourself by default. Do not spawn subagents except for necessary independent reviews or when I explicitly ask you to.
